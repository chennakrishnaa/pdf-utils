# Independent review (T8)

## Verdict
1. **Private, supervised trial: yes, with caveats.** The security claims hold on both built APKs: no permissions, only `MainActivity` exported, no network code, backups off. All four features work on the tested fixtures with real MuPDF, on the host and on an Android 12 x86_64 emulator.
2. **Wider distribution: no.** The AGPL source URL is still a placeholder (`https://example.invalid/...`). The release APK is unsigned, R8 is off, and it has never been installed. There are no notices for MuPDF's bundled third-party libraries.
3. **Fix first (High):** saving can leave a truncated or empty file at the user's chosen location, sometimes with no message (H1). PDFs encrypted with only an owner password are accepted, and merge strips their encryption and restrictions (H2).

Checked and found correct: every MuPDF object is destroyed in `ImagePages`, `MergeOp`, `CompressOp` (`Scope` guards `PDFObject.Null` and the `ColorSpace.Device*` singletons) and `PdfInputs.open` (destroys the doc on failure). There is no `PDFObject.push(PDFObject)` or `addObject` in main. All engine calls run on one `pdf-engine` thread. `out` is only written by the final save and is deleted on `Err`. Inputs are only read. Compress falls back to a byte copy when the result is not smaller, and only replaces an image stream when the new one is strictly smaller. A progress total of 0 shows an indeterminate bar, and Compress reports `(1,1)` when there are no images. Icon buttons have content descriptions. No hardcoded UI strings were found.

The following are not proven for any feature:
- No feature screen has run with the real engine. No system picker or create-document flow has run on a device; the on-device tests call `PdfJobs` with test-provided Uris.
- The release build has never been installed or run. It is unsigned, and R8 is off (`isMinifyEnabled = false`), so the keep rules are untested.
- The arm64 `.so` has never been executed. The emulator is x86_64 and the host tests use a separately built library.
- Only Android 12 has been tested. Nothing has run on API 26–30 (the `BitmapFactory` and manual-EXIF branch runs only under Robolectric), API 33+ (the native photo picker) or Android 15/16.
- 32-bit devices are excluded by design: there is no armeabi-v7a build.
- Process death, low memory and a full disk have not been tested.
- Truncated destinations and destinations whose provider rejects `"wt"` have not been tested.
- No accessibility audit (TalkBack, font scaling) has been done.

## Risks and decisions for the owner
- **AGPL obligations:** publish the exact corresponding source for every distributed APK and put the real URL in `source_code_url` (B1). Add third-party notices for the libraries in MuPDF and AndroidX (M6). Decide whether the dev files (L9) belong in the public repo. Distributing through Google Play is compatible with AGPL only if the source offer is honoured.
- **Encrypted-input policy:** decide whether PDFs with only an owner password are rejected, as the design rule says, or processed. If processed, decide whether merge may strip their restrictions (H2).
- **Device coverage:** 32-bit devices cannot install the app, and some low-end or Go devices are 32-bit only. Decide whether that is acceptable. Test at least one physical arm64 phone on API 26–29 and one on API 34+ before release.
- **Release pipeline:** add signing, decide on R8 (and test with it), and decide on an app-bundle versus APK size budget. The release dex is about 26 MB unminified.
- **Dependencies:** MuPDF Android binaries come from Artifex's own Maven repository. There is no checksum pinning (L8), and the host test library is hand-built (L10). MuPDF releases often and has regular security fixes for parser bugs. The app opens untrusted PDFs in-process, so plan to update MuPDF promptly.
- **Before a trial:** fix H1 at least, by deleting the destination document on failure or cancel and disabling Discard and Back while saving. Ideally also fix M1, M2 and M4, which are cheap and user-visible.
